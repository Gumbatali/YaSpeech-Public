# Диаризация через pyannote.audio — план

## Контекст

Сейчас в проде (`apps/server/src/infrastructure/pyannote-diarization.js`)
диаризация спикеров вызывается через HuggingFace Inference API по HTTP
(`pyannote/speaker-diarization-3.1`), опционально — если задан `HF_TOKEN`.
Без токена шаг пропускается, и приложение "угадывает" спикеров через LLM
по тексту транскрипта — менее надёжно на похожих голосах / перекрывающейся
речи.

Цель этого плана — проверить, даёт ли **локальный** pyannote.audio pipeline
(модель `pyannote/speaker-diarization-3.1` через библиотеку `pyannote.audio`
4.x, а не HTTP API) заметно лучшее качество и приемлемое время обработки,
прежде чем решать, стоит ли встраивать его в прод (Фаза B — контейнер/деплой,
**не в рамках этого плана**, отдельный запрос).

## Фаза A — Валидация (эта фаза)

1. Поднять Python venv, поставить `pyannote.audio>=4,<5` и зависимости
   (`torch`, `torchaudio`).
2. Написать скрипт `scripts/experiments/pyannote-validation/run_diarization.py`,
   который:
   - грузит pipeline `pyannote/speaker-diarization-3.1` с HF-токеном
     (`token=` — в 4.x параметр `use_auth_token` переименован);
   - прогоняет её на реальном аудиофайле из `~/Downloads`;
   - в 4.x результат диаризации получают через `pipeline(file).speaker_diarization`
     (объект `Annotation`), а не старым способом через `pipeline(file)` напрямую
     с `itertracks` на корневом результате — обёртка `SpeakerDiarizationOutput`
     появилась начиная с 4.x;
   - печатает список сегментов (спикер, start, stop) и время обработки.
3. Прогнать на 1–2 реальных записях звонков/встреч из `~/Downloads`.
4. Сравнить на слух результат диаризации с текущим LLM-угадыванием спикеров
   в приложении на том же аудио.
5. Зафиксировать в README:
   - число найденных спикеров;
   - время обработки relative real-time (processing time / audio duration);
   - качественную оценку (совпадает/не совпадает с реальными репликами).

## Фаза B — Контейнеризация и деплой (НЕ делать без отдельного запроса)

Только после явного одобрения по итогам Фазы A: упаковка в контейнер
(из-за веса torch/pyannote — это отдельный сервис, а не часть основного
Node.js бэкенда), деплой, интеграция вместо/вместе с HF Inference API.

## Статус на 2026-07-30

Инфраструктурное ограничение текущего окружения (облачная сессия
Claude Code): исходящий сетевой доступ к PyPI заблокирован политикой сети
окружения (`pip install` → 403 на `pypi.org`), поэтому `pyannote.audio`
здесь установить не удаётся. `~/Downloads` в этой сессии также пуст —
тестовых аудиофайлов нет. Реальный прогон Фазы A должен выполняться
в среде с доступом к PyPI/HuggingFace и с тестовыми аудиофайлами
(например, локально у разработчика или в окружении с более открытой
сетевой политикой). Скрипт и README подготовлены и готовы к запуску —
см. `scripts/experiments/pyannote-validation/`.
