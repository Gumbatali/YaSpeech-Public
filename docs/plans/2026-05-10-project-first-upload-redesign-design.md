# Project-First Upload Redesign Design

**Date:** 2026-05-10

## Goal

Перестроить MVP в более понятный для не-технического пользователя интерфейс, где основной сценарий начинается с выбора проекта слева и большой загрузки записи справа. После транскрипции система предлагает черновое название встречи и черновой список спикеров, а затем по подтверждению пользователя собирает итоговый протокол.

## Product Direction

Главный принцип: интерфейс должен выглядеть как простой рабочий инструмент, а не как инженерная панель.

- Сначала пользователь выбирает проект.
- Затем загружает одну запись встречи.
- Система последовательно показывает стадии обработки.
- После транскрипта появляется черновик: название встречи, спикеры, фрагмент транскрипта.
- После подтверждения запускается финальная сборка протокола.

## UX Structure

### Left Rail

- Список проектов.
- Кнопка создания проекта.
- Для выбранного проекта:
  - действие `Загрузить запись`;
  - действие `Прошлые встречи`;
  - спокойная подсказка о команде проекта.

### Right Workspace

Состояния рабочей области:

1. `Нет проекта`
   - текст `Выберите проект слева`.
2. `Проект выбран`
   - крупный заголовок проекта;
   - заметная зона загрузки файла;
   - короткий список участников проекта;
   - человекочитаемое объяснение, что система сначала подготовит текст, затем предложит название и участников.
3. `Идёт обработка`
   - пошаговый прогресс:
     - `Запись загружена`
     - `Готовим текст встречи`
     - `Определяем спикеров и название`
     - `Черновик готов`
4. `Черновик`
   - editable-поле `Название встречи`;
   - список спикеров вида `Спикер 1`, `Спикер 2`;
   - если имя найдено, показываем уверенный или предполагаемый вариант;
   - фрагмент транскрипта по спикерам;
   - одна главная кнопка `Собрать протокол`.
5. `Результат`
   - название встречи;
   - краткое резюме;
   - решения;
   - задачи;
   - полный протокол;
   - транскрипт по спикерам;
   - кнопки `Скопировать` и `Скачать TXT`.

## Architecture Constraints

Нельзя добавлять новый технологический стек. Решение должно оставаться внутри уже согласованного контура:

- фронтенд как статический сайт;
- backend как лёгкая обёртка поверх Yandex Cloud сервисов;
- прямой upload в `Object Storage`;
- асинхронная обработка через очередь;
- распознавание в speech-слое;
- смысловая пост-обработка через `AI Studio`, если она допускается итоговой интеграцией.

## Cost-Conscious Cloud Shape

Для первой версии ориентируемся на максимально экономный serverless-контур:

- `Object Storage`:
  - публичная раздача SPA;
  - приватное хранение аудио и артефактов.
- `API Gateway`:
  - лёгкий HTTP-вход для интерфейса.
- `Cloud Functions`:
  - CRUD и orchestration.
- `Message Queue`:
  - отложенная обработка после загрузки.

Почему так:

- нет постоянно работающей виртуальной машины;
- почти весь ресурс тратится только по запросу;
- большие файлы идут напрямую в storage, а не через gateway;
- это легче потом заменить с локальных mock-интеграций на реальные Yandex adapters.

## Data Model Impact

Существующее хранилище можно сохранить. Понадобится только расширить представление встречи в UI:

- `meeting.titleDraft`
- `meeting.speakerDrafts`
- `meeting.transcriptPreview`
- `meeting.protocol`

Если реальные интеграции пока не подключены, локальные mock-адаптеры должны возвращать эти поля, чтобы интерфейс можно было проверить до облачного этапа.

## Interaction with AI

Промптованный анализ должен происходить после получения транскрипта, а не вместо него.

Система передаёт:

- транскрипт;
- название проекта;
- список участников проекта.

Система ожидает в ответ:

- короткое название встречи;
- список спикеров;
- попытку сопоставления имён по содержанию речи;
- резюме;
- решения;
- задачи;
- транскрипт в разрезе спикеров.

## Risks

- Определение имён спикеров остаётся вероятностным.
- Для одного микрофона и множества участников имена не могут считаться достоверными без подтверждения пользователя.
- Поэтому черновой шаг подтверждения обязателен для качественного MVP.

## Success Criteria

- Пользователь без технического контекста понимает главный сценарий с первого экрана.
- Основной путь занимает один экран проекта и не требует навигации по нескольким разделам.
- Статусы обработки читаются как обычные пользовательские сообщения.
- Интерфейс можно без больших переделок развернуть в Yandex Cloud serverless-контуре.
