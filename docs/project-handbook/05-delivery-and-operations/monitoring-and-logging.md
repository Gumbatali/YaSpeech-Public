# Мониторинг и логи

Как понять, что сервис жив, и где смотреть, когда что-то сломалось. Заточено под
одного оператора — без тяжёлого стека Prometheus/Grafana, которого тут пока не
нужно.

---

## Уровень 0: жив ли сервис

Самое дешёвое и важное — внешний healthcheck.

**[Healthchecks.io](https://healthchecks.io)** (бесплатный тариф):

1. Создай check с расписанием «каждые 5 минут».
2. Настрой простой пинг прод-URL (через их «ping by URL» или внешний cron).
3. Подключи уведомление в Telegram / на почту.

Если сайт лёг — придёт алерт за минуты, а не «когда заметит пользователь».

> Альтернатива: UptimeRobot, Better Uptime — любой внешний аптайм-монитор.

---

## Уровень 1: логи функций (встроено в Yandex Cloud)

Обе Cloud Functions пишут в **Cloud Logging** автоматически. Ничего настраивать
не нужно.

**Где смотреть:** консоль YC → Logging → группа логов фолдера, либо через CLI:

```bash
# последние логи worker-функции
yc logging read --group-name default --filter 'resource_id="<worker-fn-id>"' --since 1h

# поиск по конкретной встрече (в логах есть meetingId)
yc logging read --group-name default --filter 'json_payload.meetingId="<meetingId>"'
```

Код логирует структурированно через `apps/server/src/shared/logger.js` — у записей
есть `meetingId`, стадия и код ошибки. Это позволяет связать жалобу пользователя
(«моя встреча зависла») с конкретной цепочкой логов.

### Что искать при типовых проблемах

| Симптом | Фильтр / на что смотреть |
|---------|--------------------------|
| Встреча застряла | логи worker по `meetingId`, последняя стадия |
| Протокол не собрался | ошибки с кодом `YANDEX_GPT_ERROR` |
| Расшифровка не вышла | `SPEECHKIT_ERROR` / `SPEECHKIT_TIMEOUT` / `POOR_TRANSCRIPT` |
| Refine упал | `refine failed`, поле `llmRefine.status=failed` |

Подробный разбор сценариев — в [runbook.md](./runbook.md).

## Уровень 2: алерты на ошибки (опционально)

Когда захочется узнавать об ошибках, не заходя в консоль:

**Yandex Monitoring** (встроен, бесплатные базовые метрики):

- метрики функций: число вызовов, ошибки, длительность, память;
- алёрт «error rate worker-функции > N за 5 минут → уведомление»;
- канал уведомлений: Telegram-бот или email.

Этого достаточно для текущего масштаба. Полноценный Prometheus + Grafana имеет
смысл только когда появится постоянный заметный трафик и несколько сервисов.

## Уровень 3: очередь не копится

Worker обрабатывает встречи через YMQ. Если worker систематически падает,
сообщения копятся в очереди.

**Где смотреть:** консоль YC → Message Queue → `yaspeech-queue` → метрики
«In-flight» и «Messages available». Здоровое состояние — почти ноль в покое.
Стабильно растущее число = worker не справляется или падает на одном и том же.

## Чего здесь сознательно НЕТ (и почему)

| Инструмент | Почему не сейчас |
|-----------|------------------|
| Prometheus + Grafana | Избыточно для serverless с одним оператором; Cloud Monitoring закрывает потребность |
| ELK / Loki | Cloud Logging уже индексирует и ищет по логам |
| Jaeger / трейсинг | Пайплайн линейный и короткий; `meetingId` в логах хватает для трассировки |

Эти инструменты окупятся, когда: появится постоянный трафик (сотни запросов в
минуту), несколько сервисов помимо функций, или команда эксплуатации больше
одного человека.

## Минимальный чек-лист оператора

- [ ] Внешний healthcheck на прод-URL с уведомлением (Уровень 0).
- [ ] Знаю, как открыть логи worker по `meetingId` (Уровень 1).
- [ ] Раз в неделю заглядываю в метрики очереди и ошибок функций.
