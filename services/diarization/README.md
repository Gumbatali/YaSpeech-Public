# Сервисы диаризации

Шесть бэкендов разделения по спикерам за одним HTTP-контрактом. Собраны, чтобы
сравнить их на одном корпусе и выбрать, что ставить в прод, — а не чтобы
запускать все шесть одновременно.

## Зачем это вообще

В проде диаризацию делает Яндекс SpeechKit: он возвращает `speakerTag` вместе
с текстом. Отдельный диаризатор нужен, если использовать Whisper для текста
(он точнее на русском), потому что Whisper спикеров не различает вовсе.

## Измеренные результаты

Замер на **VoxConverse dev** (реальные YouTube-записи с ручной RTTM-разметкой):
8 записей, 31 минута, 3–6 спикеров, перекрытия 18–33%. CPU-инстанс
16 vCPU / 64 ГБ, без GPU. Дата: 2026-08-04.

| Бэкенд | DER | miss | FA | spk-err | RTF | Файлов |
|--------|-----|------|-----|---------|-----|--------|
| **streaming-sortformer** v2.1 | **6.1%** | 2.5% | 1.0% | 2.6% | 0.02× | 8/8 |
| nemo-sortformer v1 | 11.9% | 4.3% | 1.2% | 6.4% | 0.06× | 8/8 |

Streaming оказался лучше **на всех 8 записях из 8** и втрое быстрее.
Это противоречит ожиданию «потоковая модель хуже offline, потому что не видит
будущий контекст» — вероятная причина в версиях: streaming это v2.1, а
offline-чекпоинт v1. Сравниваются не столько режимы, сколько поколения модели.

### Влияние лимита в 4 слота — измерено

| Записи | DER | spk-err |
|--------|-----|---------|
| ≤4 спикеров (n=4) | 5.8% | 2.1% |
| >4 спикеров (n=4) | 17.9% | 10.6% |

Обе модели физически не могут выдать больше 4 спикеров: на всех записях с 5–6
участниками они выдавали ровно 4. Ошибка при этом растёт втрое, а неверная
атрибуция реплик — впятеро. Худший случай — запись с 6 спикерами: у
offline-модели DER 34.7%.

**Практический вывод:** если на планёрках бывает больше четырёх говорящих,
Sortformer будет систематически путать реплики, и никакой настройкой это не
лечится. Для такого случая нужен pyannote или diart, где число спикеров —
параметр, а не свойство архитектуры.

## Что есть и чего от каждого ждать

| Бэкенд | Порт | Спикеров | GPU | Статус замера |
|--------|------|----------|-----|---------------|
| `streaming-sortformer` | 8003 | ровно 4 слота | не обязателен | ✅ **6.1% DER** |
| `nemo-sortformer` | 8002 | ровно 4 слота | не обязателен | ✅ 11.9% DER |
| `pyannote` (self-hosted) | 8001 | любое, параметром | опц. | ⏸ нужен HF-токен |
| `diart` | 8004 | не ограничено | опц. | ⏸ нужен HF-токен |
| `eend-eda` | 8005 | до 6 | опц. | ⏸ нужен чекпоинт |
| `pyannote-hf` | — | любое | — | ⏸ нужен HF-токен |

Оба Sortformer'а **работают на CPU** — GPU ускоряет, но не требуется: RTF 0.02×
означает, что час записи обрабатывается примерно за минуту на 16 ядрах.

Три бэкенда с пометкой ⏸ не замерены: веса pyannote и diart закрыты лицензией
(нужен HF-токен с принятыми условиями), а для EEND-EDA нужен чекпоинт CALLHOME,
который качается вручную. Как только токен появится — они прогоняются той же
командой, менять код не нужно.

**Про eend-eda ожидание остаётся прежним:** чекпоинт обучен на английской
телефонной речи 8 kHz, поэтому на русской планёрке результат будет слабым.
Его ценность — честная цифра «сколько стоит взять research-модель как есть».

Подробности — в docstring в начале каждого `app.py`.

## Быстрый старт (локально)

```bash
cd services/diarization
export HF_TOKEN=hf_...           # нужен для pyannote и diart
mkdir -p models

docker compose up pyannote        # самый простой — работает и на CPU
curl http://localhost:8001/health
```

`/health` отвечает `503` пока веса грузятся — это нормально, на холодном
старте уходит от десятков секунд до пары минут.

Проверить на своём файле:

```bash
curl -F audio=@meeting.wav -F num_speakers=3 http://localhost:8001/diarize
```

GPU-сервисы (нужен `nvidia-container-toolkit`):

```bash
docker compose --profile gpu up nemo-sortformer
```

## Замер DER

Сравнение имеет смысл только на размеченных данных. Готовим синтетический
корпус — эталон известен по построению:

```bash
# 1. Нужны моно-WAV 16 kHz, по одному файлу на голос (≥3 файлов).
#    Можно нарезать из Golos: scripts/benchmark/download_golos.py
python3 scripts/benchmark/make-synthetic-corpus.py \
  --voices ./voices --out scripts/benchmark/data/synthetic \
  --sessions 10 --speakers 3 --duration 300 --overlap-ratio 0.12

# 2. Прогнать все поднятые бэкенды разом
node scripts/benchmark/run-diarization-benchmark.mjs \
  --manifest scripts/benchmark/data/synthetic/manifest.jsonl \
  --backend pyannote=http://localhost:8001 \
  --backend nemo-sortformer=http://localhost:8002
```

Вывод — таблица с DER и разложением ошибки на miss / false alarm / speaker
error, плюс JSON-отчёт рядом с манифестом.

**Важно про синтетику.** Она честно моделирует структуру разговора (число
участников, чередование, перебивания), но не моделирует акустику: реверберацию,
шум стройки, удалённый микрофон. Поэтому она годится, чтобы **ранжировать**
бэкенды между собой, но абсолютные значения DER будут оптимистичнее, чем на
реальных записях. Для чисел, которые можно обещать заказчику, нужен размеченный
корпус настоящих планёрок.

### Как читать метрики

- **DER** — суммарная доля ошибочного времени. Ниже лучше. Может быть >100%,
  если система выдумывает речь сверх эталонной.
- **miss** — эталон говорит, система молчит.
- **FA** (false alarm) — система говорит, эталон молчит.
- **spk-err** — речь найдена, но приписана не тому спикеру. Именно эта
  составляющая портит протокол сильнее всего: реплики уходят чужому человеку.
- **N спик.** — доля записей, где число участников угадано точно.
- **RTF** — доля реального времени: `0.5×` значит вдвое быстрее записи.

## Подключение к YaSpeech

Выбранный бэкенд включается двумя переменными в `scripts/.env.deploy`:

```bash
ASR_PROVIDER=smart              # Whisper для текста + отдельный диаризатор
DIARIZER=pyannote-selfhosted
DIARIZER_URL=http://<ip>:8000
GROQ_API_KEY=gsk_...
```

Дальше обычный `./scripts/deploy.sh worker`. Таймаут воркера при
`ASR_PROVIDER=smart` автоматически поднимается с 60s до 600s — внешняя
диаризация занимает минуты, в прежний лимит она не укладывалась.

Если ничего не задавать, всё работает как раньше — на SpeechKit.

## Деплой в облако

```bash
# 1. Реестр (один раз)
yc container registry create --name yaspeech-diarization

# 2. Собрать и опубликовать
./deploy/build-and-push.sh pyannote --registry <id> --push

# 3. Инстанс — сначала предпросмотр, деньги не тратятся
./deploy/create-instance.sh pyannote --registry <id> --sa <id> --subnet <id>
# и только потом, осознанно:
./deploy/create-instance.sh pyannote ... --confirm
```

⚠️ **GPU-инстанс тарифицируется за время существования, а не за запросы.**
Круглосуточный T4 — это десятки тысяч рублей в месяц независимо от нагрузки.
Для экспериментов дешевле поднять на час, прогнать бенчмарк и удалить:

```bash
yc compute instance delete yaspeech-diar-pyannote
```

Для `pyannote` и `eend-eda` есть флаг `--cpu-only` — на порядок дешевле.

## Веса моделей

Монтируются томом в `/models`, в образы не вшиты (образ NeMo и так ~20 ГБ).

- **pyannote, diart** — качаются автоматически при первом старте, нужен
  `HF_TOKEN` и принятые условия лицензии на huggingface.co.
- **NeMo Sortformer** — качается автоматически с NGC.
- **EEND-EDA** — чекпоинт нужно скачать вручную из
  [BUTSpeechFIT/EEND](https://github.com/BUTSpeechFIT/EEND) и положить в
  `models/eend/callhome.pth`. Без него сервис честно ответит `503` с
  понятным сообщением, а не упадёт молча.

## Контракт

Описан в
[`apps/server/src/infrastructure/diarization/contract.md`](../../apps/server/src/infrastructure/diarization/contract.md).
Коротко: `POST /diarize` с `multipart/form-data`, ответ — сегменты
`{speaker, start, stop}` в секундах. Перекрытия разрешены и не считаются
ошибкой. Node-адаптер при любой ошибке сервиса возвращает `null`, и встреча
обрабатывается без разделения по спикерам — пайплайн не падает.
