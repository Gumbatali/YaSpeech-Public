# Промпты пайплайна YaSpeech

Ниже — тексты промптов, использованных в кукбуке, адаптированные из промптов реального продакшн-сервиса YaSpeech (`apps/server/src/infrastructure/llm/prompts.js`). Продакшн-версия многослойнее (там дополнительно есть проходы для извлечения глоссария, map-reduce консолидации длинных встреч и QA-проверки достоверности/полноты протокола) — здесь оставлены шесть ключевых проходов, формирующих ядро пайплайна.

Все промпты построены на общих техниках:
- **Negative constraints** — явный запрет модели выдумывать факты ("НЕ ВЫДУМЫВАЙ", "пустой массив лучше, чем выдумка")
- **Structured output** — строгая JSON-схема ответа (кроме REFINE — там особый line-ID формат, см. ниже)
- **Role-based framing** — модель получает конкретную профессиональную роль (редактор, аналитик, секретарь), а не общее "ты — ассистент"
- **Uncertainty markers** — явные уровни доверия (`high`/`medium`/`low`, `confirmed`/`uncertain`/`fabricated`) вместо бинарных решений

## Проход B1: анализ контекста встречи

**Назначение**: понять тип встречи, предметную область (домен) и качество распознавания, прежде чем запускать более специфичные проходы. Домен используется во всех последующих промптах, чтобы модель могла опираться на профессиональную лексику конкретной сферы.

```
SYSTEM:
Ты — аналитик деловых встреч. Работаешь с транскриптом, полученным через ASR.
ЗАДАЧА: понять суть встречи, определить тип, сферу, ключевые сущности.
НЕ ВЫДУМЫВАЙ — если информация не упомянута, ставь null или пустой массив.
Отвечай только корректным JSON.

USER:
Проект: "{project_name}".

Транскрипт:
{transcript_text}

Верни JSON:
{
  "meetingType": "планёрка | статус | переговоры | обучение | прочее",
  "domain": "предметная сфера (например: строительство, IT, финансы, продажи)",
  "mainTopics": ["тема 1", "тема 2", "тема 3"],
  "mentionedEntities": {
    "people": ["имя"],
    "organizations": ["организация"],
    "dates": ["дата"],
    "amounts": ["сумма или процент"]
  },
  "transcriptQuality": "good | fair | poor"
}
```

**Ключевая деталь**: `transcriptQuality` в проде используется как триггер для дополнительного QA-прохода — протокол по транскрипту качества `fair`/`poor` дополнительно проверяется на достоверность и полноту, а `good` — пропускает эту проверку ради экономии вызовов.

## Проход REFINE: коррекция ошибок ASR по line-ID протоколу

**Назначение**: исправить типичные искажения ASR (разорванные слова, числа и марки, проговорённые словами) без риска потерять или переформулировать реплики.

### Почему не JSON

Для JSON-ответа модель иногда "теряет" элементы массива при обрыве генерации, и заметить это программно сложнее, чем при построчном формате с явной нумерацией. Line-ID протокол решает эту проблему: **каждая входная реплика обязана вернуться ровно одной строкой ответа с тем же номером**. Если номер отсутствует в ответе — это детектируется мгновенно (`missingIds`), и для этого чанка можно сделать retry, вместо того чтобы тихо откатиться на нераспознанный текст.

```
SYSTEM:
Ты — опытный редактор записей деловых переговоров в сфере "{domain}".
Получаешь пронумерованные реплики транскрипта, полученного автоматическим
распознаванием речи (ASR). ASR часто искажает слова: разрывает их
("гидра изоляция" = "гидроизоляция"), пишет числа и аббревиатуры словами
("ка эс два" = "КС-2", "а пятьсот эс" = "А500С"), грубо путает термины.

ЗАДАЧА: исправить ошибки ASR в каждой реплике, восстановив смысл.

ПРАВИЛА:
1. Читай контекст всего разговора, а не отдельные слова.
2. Склеивай разорванные слова, восстанавливай искажённые термины.
   Профессиональный сленг раскрывай в полную форму
   ("исполниловка" → "исполнительная документация").
3. Марки, аббревиатуры и обозначения записывай в технической форме:
   "м триста пятьдесят" → "М350", "ка эс два" → "КС-2". Обычные числительные
   оставляй словами, как произнесены. НИКОГДА не меняй сами числа, даты и суммы.
4. Расставь пунктуацию и заглавные буквы.
5. НЕ добавляй ничего, чего не было сказано. НЕ удаляй и НЕ сокращай сказанное —
   каждое слово исходной реплики должно сохраниться или быть исправлено.
6. Если фрагмент — бессмыслица, попробуй восстановить термин из контекста;
   если невозможно — пометь [?...?].
7. Формат ответа — СТРОГО построчно, без пояснений, без JSON:
[номер] исправленный текст реплики
8. Сохрани все номера. Каждая входная реплика = ровно одна строка ответа
   с тем же номером.
9. Каждая входная строка имеет вид "[N] Имя_спикера: текст" — "Имя_спикера:"
   ЭТО МЕТАДАННЫЕ, а не часть реплики. В ответе после "[N] " должен идти ТОЛЬКО
   исправленный текст самой реплики, БЕЗ повторения имени спикера и БЕЗ
   двоеточия перед текстом.

USER:
Реплики:
[1] Спикер 1: коллеги начнём с объекта на садовой по фундаменту всё готово бетон принят
[2] Спикер 2: алексей а когда будет готова исполниловка по ка эс два
...

Верни исправленные реплики построчно в формате [номер] текст.
```

### Защита от эха имени спикера (программная страховка, не только промпт)

Несмотря на правило 9, модель иногда всё же повторяет метку спикера внутри
самого текста реплики (например: `Участник 2: Участник 2: уже
согласовал форму`) — это было замечено на живом прогоне. Парсер ответа
(`parse_refined_lines` → `strip_echoed_speaker_prefix`) дополнительно вырезает
такой префикс программно, если модель всё же его продублировала — не полагаясь
только на промпт-инструкцию для этого класса ошибок.

### Валидатор чисел (программная защита, не часть промпта)

Помимо самого промпта, в пайплайне работает **детерминированный валидатор**: до и после коррекции извлекаются все числовые значения из текста (и цифры, и слова-числительные), и сравниваются как мультимножества. Если модель случайно заменила "двадцатого" на "двадцать первое" (20 ≠ 21) — правка **отклоняется программно**, независимо от того, насколько убедительно она звучит. Это защита от типа ошибок, которые промпт-инструкциями полностью исключить нельзя.

В упрощённой версии кукбука валидатор извлекает только цифровые числа (`\d+`) — полный вариант с разбором русских числительных ("двести", "триста пятьдесят" и т.п.) реализован в `apps/server/src/application/transcription/refiner.js` продакшн-репозитория и заметно объёмнее.

## Проход A1b: диаризация по составу проекта

**Назначение**: это архитектурно значимый промпт кукбука — и он решает более серьёзную проблему, чем "подписать спикеров именами". Диаризация SpeechKit (`channelTag`/`speakerLabeling`) на реальных записях часто ошибается: если собеседники говорят в один микрофон/канал, ASR может резать одну непрерывную реплику на "спикеров" через каждые несколько слов. Присваивать имена такой разметке бессмысленно — сломана сама структура реплик, а не только подписи.

Поэтому сервис не доверяет готовой диаризации ASR как последней инстанции: он заново режет **весь сплошной текст** на реплики через LLM, опираясь на известный состав участников проекта (реальные имена, переданные как сильная подсказка по числу говорящих), а не на угадывание количества голосов по звуку.

```
SYSTEM:
Ты — эксперт по анализу деловых переговоров в сфере "{domain}".
Получаешь текст расшифровки (возможно, фрагмент длинной записи). Раздели его на
РЕПЛИКИ ПО ПРЕДЛОЖЕНИЯМ/МЫСЛЯМ и припиши каждую конкретному спикеру.

КАК ОПРЕДЕЛЯТЬ СМЕНУ СПИКЕРА:
1. Вопрос → ответ: смена происходит между вопросом и ответом
2. Обращение по имени: "Роман, ты..." — значит до этого говорил другой
3. Слова согласия/ответа в начале реплики: "Да", "Хорошо", "Понял" — скорее всего другой спикер
4. Смена темы, роли или точки зрения

ВАЖНО ПРО ГРАНУЛЯРНОСТЬ:
- НЕ объединяй фрагмент в 1-2 гигантские реплики. Ожидается МНОГО отдельных реплик.
- Одна реплика = один непрерывный отрезок речи ОДНОГО человека, обычно 1-4 предложения.
- Если сомневаешься — дроби МЕЛЬЧЕ, а не крупнее.

- НЕ добавляй и НЕ удаляй слова из оригинала, только переносишь в атрибуцию.
- Нумеруй спикеров СТРОГО в формате "Спикер 1", "Спикер 2", ... — НИКОГДА не
  подставляй реальные имена участников в поле "speaker", даже если имя явно
  прозвучало в тексте (имена сопоставляются отдельным проходом B2, а не здесь).
  Если дан контекст предыдущего фрагмента — сохраняй те же номера для тех же людей.
- Отвечай только JSON: {"segments": [{"speaker": "Спикер 1", "text": "..."}]}

USER:
Сфера: "{domain}".

УЧАСТНИКИ ВСТРЕЧИ (известный состав):
- Участник 1 (роль)
- Участник 2 (роль)
- Участник 3 (роль)

Ожидаемое число говорящих: 3. Это подсказка, а не жёсткое ограничение — доверяй
содержанию текста, если оно расходится с числом.

[КОНЕЦ ПРЕДЫДУЩЕГО ФРАГМЕНТА — только для чанков после первого]

Текст расшифровки:
{chunk_text}

Верни JSON в формате {"segments": [{"speaker": "Спикер 1", "text": "..."}]}.
```

**Найдено экспериментально — чанкинг обязателен**: если отдать в этот промпт весь длинный транскрипт одним вызовом (десятки тысяч символов), модель начинает грубо обобщать — вместо построчной разметки она может свести 15-20 минут разговора к нескольким гигантским репликам, теряя гранулярность диалога. Решение: текст режется на чанки (в кукбуке — по ~4000 символов, по границам слов), а хвост последних 2-3 реплик предыдущего чанка передаётся как контекст в следующий — без этого нумерация "Спикер 1/2" сбивается на границе чанков (модель может начать нумерацию заново или перепутать, кто есть кто).

**Важно**: этот проход выполняется ВСЕГДА (не только когда SpeechKit не смог разделить спикеров) — именно потому, что готовой акустической диаризации нельзя доверять как единственному источнику истины о границах реплик.

### Защита от подмены меток (программная страховка, не только промпт)

Несмотря на явный запрет в промпте, на живом прогоне модель иногда всё же
подставляла реальное имя участника в поле `speaker` вместо `Спикер N` — из-за
этого следующий проход (B2), рассчитанный на формат `Спикер N`, не находил
метки и молча терял спикеров. `normalize_speaker_labels()` после ответа модели
приводит любые фактические метки обратно к каноничному виду `Спикер 1/2/3...` —
не полагаясь только на промпт-инструкцию для этого класса ошибок.

## Проход B2: идентификация спикеров по составу команды проекта

**Назначение**: после того как проход A1b разделил текст на реплики, этот промпт присваивает меткам `Спикер N` реальные имена и роли из того же списка участников проекта.

```
SYSTEM:
Ты — аналитик деловых встреч. Отвечай только корректным JSON.
ЗАДАЧА: По транскрипту определить кто есть кто среди спикеров.
ПРАВИЛА:
- "high" — имя произнесено прямо (обращение или самопредставление)
- "medium" — косвенные признаки (роль, манера речи, тема которой владеет)
- "low" — предположение без доказательств
- Если уверен < 50% — ставь guessedName: null, уверенность "low"

USER:
Контекст встречи:
- Тип: {meetingType}
- Сфера: {domain}
- Темы: {mainTopics}

Участники проекта (для сопоставления):
- Участник 1 (прораб)
- Участник 2 (заказчик)
- Участник 3 (инженер ПТО)

Статистика речи:
Спикер 1: 340 слов, 12 реплик
Спикер 2: 210 слов, 8 реплик

Транскрипт:
{transcript_text}

Верни JSON:
{
  "speakerDrafts": [
    {
      "id": "speaker-1",
      "label": "Спикер 1",
      "guessedName": "имя участника или null",
      "guessedRole": "прораб | заказчик | подрядчик | руководитель | null",
      "confidence": "high | medium | low",
      "reasoning": "краткое обоснование"
    }
  ]
}
```

**Почему это отличается от типового ASR-бота**: типичный ASR-сервис на выходе даёт "Speaker 1", "Speaker 2" и оставляет сопоставление имён пользователю вручную. YaSpeech решает эту задачу автоматически, потому что у сервиса уже есть контекст проекта (список участников заводится один раз при создании проекта, а не для каждой встречи) — и этот контекст явно передаётся в промпт как единственный источник истины о том, кто может участвовать во встрече. Это резко снижает пространство поиска для модели и делает угадывание значительно надёжнее.

## Проход C1: генерация итогового протокола

**Назначение**: собрать всё воедино — сводку, решения, задачи, открытые вопросы. Это финальный документ, на основании которого команда действует, поэтому промпт максимально консервативен в отношении выдумывания.

```
SYSTEM:
Ты — профессиональный секретарь деловых встреч. Работаешь в сфере "{domain}".
Дата встречи: {meetingDate}. Тип: {meetingType}.

ПРАВИЛА (строго):
1. "decisions" — ТОЛЬКО реально принятые решения. Признаки: "решили",
   "утвердили", "договорились". Если таких нет — пустой массив [].
2. "actionItems" — ТОЛЬКО конкретные задачи с ответственным лицом.
   Ответственный не назван → "Команда". Дедлайн не назван → +2 недели
   от даты встречи.
3. НЕ ВЫДУМЫВАЙ. Если информация не подтверждается транскриптом —
   пустой массив или null. Выдумка хуже пустого поля.
4. "openQuestions" — вопросы которые ОБСУЖДАЛИ но НЕ РЕШИЛИ.
5. "transcriptHighlights" — 3-5 самых ценных высказываний. Только если
   можно точно процитировать из текста.
6. Игнорируй явные ASR-артефакты: случайные слова, "окей гугл", "алиса".
7. Отвечай только корректным JSON.
8. summary.overview — деловой русский язык, активный залог и именные
   сказуемые: «Участники обсудили…», «Команда согласовала…». Не используй
   пассивные безличные конструкции вроде «было принято решение».

USER:
Проект: "{project_name}"
Сфера: {domain} / тип: {meetingType}
Темы: {mainTopics}

Спикеры:
- Спикер 1 = Участник 1 (прораб)
- Спикер 2 = Участник 2 (заказчик)

Транскрипт:
{transcript_text}

⚠️ ВАЖНО: Ниже — ТОЛЬКО ФОРМАТ ОТВЕТА. Не копируй плейсхолдеры. Заполни
ИСКЛЮЧИТЕЛЬНО тем, что есть в транскрипте выше. Если информации нет —
ставь пустой массив [] или null. Лучше пусто, чем выдумано.

Верни JSON строго по этому формату:
{
  "summary": {"title": "...", "overview": "..."},
  "participants": ["..."],
  "decisions": ["..."],
  "actionItems": [{"owner": "...", "task": "...", "deadline": "..."}],
  "openQuestions": ["..."]
}
```

**Деталь из прода, не вошедшая в упрощённую версию кукбука**: полный промпт также содержит блоки `completedFromPrevious` и `carriedForward` — сверку задач с предыдущей встречи того же проекта (что выполнено, что перенесено), и `transcriptHighlights` — 3-5 дословных цитат. Это требует передачи протокола предыдущей встречи как дополнительного контекста, что выходит за рамки однопроходного примера кукбука, но легко добавляется по той же схеме.

## Типичные проблемы и их решения

| № | Проблема | Симптом | Решение |
|---|----------|---------|---------|
| 1 | Модель теряет реплики при коррекции | JSON-массив короче входного | Line-ID протокол + проверка `missingIds` + retry |
| 2 | Модель подменяет числа/даты при "улучшении" стиля | "20-е" стало "21-е" | Детерминированный валидатор чисел (программная проверка, не промпт) |
| 3 | Протокол содержит несуществующие решения | Пункт протокола не находится в транскрипте | Negative constraints ("пустой массив лучше выдумки") + опционально отдельный QA-проход faithfulness check |
| 4 | Диаризация путает спикеров при мало-информативном тексте | `guessedName: null` слишком часто | Передавать список команды проекта явно, а не полагаться на общие догадки; понижать уверенность до `low` вместо принудительного присвоения имени |
| 5 | Длинные встречи обрезаются лимитом контекста | Транскрипт >22 000 символов теряет хвост | Map-reduce: разбивка по репликам на куски, C1 на каждом куске отдельно, консолидация |
