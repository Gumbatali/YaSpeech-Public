# Требования и NFR

## Функциональные требования

### Обязательные

- система должна показывать список проектов;
- система должна позволять создать проект;
- система должна позволять управлять командой проекта;
- система должна позволять загрузить одну аудиозапись встречи;
- система должна запускать асинхронную обработку встречи;
- система должна показывать черновик названия и спикеров;
- система должна позволять подтвердить черновик;
- система должна формировать итоговый протокол;
- система должна хранить историю встреч проекта;
- система должна позволять скачать текстовый протокол.

### Желательные в следующих итерациях

- экспорт в `DOCX`;
- редактирование финального протокола;
- запись встречи из браузера;
- интеграции с внешними источниками встреч;
- сравнение с предыдущими встречами.

## Нефункциональные требования

### UX

- интерфейс должен быть понятен не техническому пользователю;
- основной сценарий должен быть удобен на телефоне;
- пользователь должен видеть понятный статус обработки.

### Производительность

- UI должен быстро открываться как статический сайт;
- пользовательский запрос не должен ждать всю обработку синхронно;
- тяжёлая обработка должна уходить в фон.

### Стоимость

- решение должно использовать минимум постоянно работающих ресурсов;
- приоритет у serverless-компонентов;
- не использовать отдельную VM без необходимости.

### Безопасность

- аудиофайлы не должны лежать в публичном бакете;
- доступ к облачным ресурсам должен идти через сервисный аккаунт;
- пользовательские данные должны логироваться аккуратно и без лишних утечек.

### Наблюдаемость

- у функций должны быть логи;
- должна быть видна стадия обработки встречи;
- ошибки должны сохраняться в состоянии встречи.

### Поддерживаемость

- доменная логика не должна зависеть от конкретного облачного провайдера;
- интеграции должны быть изолированы в инфраструктурном слое;
- mock-адаптеры должны легко заменяться на реальные.
