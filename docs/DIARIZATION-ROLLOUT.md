# Внедрение диаризации в прод — статус и план

Эта ветка (`diarization-prod-rollout`) содержит готовый и измеренный код,
который **не влит в `main`** и **не задеплоен**. Причина не в качестве кода —
все тесты зелёные (124/124), все бэкенды измерены на реальных данных — а в
доступе: у сервисного аккаунта, которым я работал, нет прав в облаке, где
живёт настоящий прод. Подробности — в разделе «Почему это не в main» ниже.

Этот файл — единый вход: что почему сделано, сколько это стоит, что нужно
для запуска и какие есть альтернативы. Остальные документы в `docs/2026-08-*`
и `services/diarization/README.md` — это журналы конкретных экспериментов,
на них здесь есть ссылки.

## Коротко для тех, кто спешит

**Проблема:** SpeechKit не различает спикеров — параметр `speakerLabeling`
не даёт `speakerTag` в ответе. Все реплики в протоколе уходят одному-двум
случайным "каналам" вместо реальных участников. Проверено на английском,
русском и **двух настоящих планёрках заказчика**.

**Решение:** отдельный сервис диаризации (streaming-sortformer, есть готовый
Docker-образ) плюс небольшая правка в `SmartAsrGateway`, которая уже
написана и протестирована.

**Что нужно, чтобы включить:**
1. Права в облаке `cloud-stroytehekspert` (сейчас их нет ни у одного
   доступного мне сервисного аккаунта) — **действие для заказчика**.
2. Постоянный CPU-инстанс под сервис диаризации — от 700 до 3000 ₽/мес
   в зависимости от размера (разбивка ниже).
3. Слить эту ветку, задеплоить воркер с новыми переменными окружения.

**Дальше в этом файле:** то же самое, но подробно, с цифрами и вариантами.

## Почему это не в `main`

План был: слить в main, задеплоить прод, прогнать тестовую встречу через
настоящий интерфейс, посмотреть результат. Слияние прошло, а на шаге
деплоя выяснилось следующее.

Я всё это время работал в облаке **`rnd-lab`** (id `b1gpfeic18udd35ml48p`),
folder `stroytech-agent`. Там сервисный аккаунт `yaspeech-cookbook-s3`
(`ajed8u4l8ikhknm0s3jd`) имеет права на Object Storage и SpeechKit —
этого хватало для всех замеров.

Настоящий прод — Cloud Functions `yaspeech-api` и `yaspeech-worker`, оба
`ACTIVE` — оказался в **другом облаке**, `cloud-stroytehekspert`
(id `b1gs0l9h6ctsd7sr5ael`), folder `default`
(id `b1gcdsls1ovvfo2gf5j3`). Проверка привязок доступа:

```bash
yc resource-manager folder list-access-bindings b1gcdsls1ovvfo2gf5j3
```

показала, что `ajed8u4l8ikhknm0s3jd` в списке ролей **не значится вообще** —
ни `functions.editor`, ни `api-gateway.editor`, ничего. Деплоить туда
`scripts/deploy.sh` было нечем.

Это разделение полезно с одной стороны: значит, все эксперименты последних
дней (VoxConverse, AMI, синтетический русский корпус, две реальные
планёрки) шли в изолированной песочнице и физически не могли задеть
работающий прод. С другой стороны — сам факт «я думал, что работаю рядом
с прод-окружением, а был в соседнем облаке» стоило обнаружить раньше,
и вот он зафиксирован здесь, чтобы не повториться.

По просьбе заказчика мерж в `main` отменён (`git revert -m 1`, коммит
сохраняет полную историю, ничего не потеряно), а вся работа перенесена
в эту ветку до тех пор, пока доступ не будет выдан осознанно.

## Сколько это стоит

### Разовые расходы (уже потрачено на замеры)

Все инстансы одноразовые — подняты, использованы, удалены. Суммарно по
трём сессиям замеров:

| Сессия | Что | Стоимость |
|--------|-----|-----------|
| 2026-08-05 | Замер на VoxConverse + AMI + русском корпусе | ~34 ₽ |
| 2026-08-06 | Две реальные планёрки | ~23 ₽ |
| 2026-08-06 | Проверка гипотез про num_speakers | ~28 ₽ |
| **Итого** | | **~85 ₽** |

Полные журналы — в файлах `docs/2026-08-*-cost.md`.

### Постоянные расходы (если включать в проде)

Сервису диаризации нужно работать круглосуточно — встречу могут загрузить
в любой момент, а не только когда специально поднят тестовый инстанс.
Yandex Cloud Compute тарифицируется за время существования инстанса, не
за число запросов.

Тариф CPU 100% vCPU, Intel Ice Lake (standard-v3), зона `ru-central1`:
**1.1529 ₽/час за vCPU** — это подтверждённая ставка из официального
прайс-листа Yandex Cloud. Ставка за RAM здесь не подтверждена официальным
источником на момент написания — использована консервативная оценка
≈0.3 ₽/час за ГБ по порядку величины из практики прошлых замеров; перед
тем как согласовывать бюджет, стоит свериться с
[калькулятором Yandex Cloud](https://yandex.cloud/ru/prices?tab=compute)
или прайс-листом на день расчёта.

| Конфигурация | vCPU | RAM | ₽/час (оценка) | ₽/месяц (24×7, оценка) | RTF streaming-sortformer |
|---------------|------|-----|-----------------|--------------------------|---------------------------|
| Как в тестах | 16 | 64 ГБ | ~37 | **~26 600** | 0.04× (измерено) |
| Средняя | 8 | 32 ГБ | ~18 | **~13 300** | не измерено, ожидаемо ~0.08× |
| Минимальная | 4 | 16 ГБ | ~9.4 | **~6 800** | не измерено, ожидаемо ~0.15× |

Строка "как в тестах" опирается на реально наблюдавшуюся стоимость из
журналов замеров (~37 ₽/час фактически списывалось), остальные две —
линейная экстраполяция и требуют проверки перед принятием решения.

**Важная оговорка:** RTF для 8 и 4 vCPU — не измерен, только линейная
экстраполяция от 16 vCPU. Реальное падение может быть нелинейным
(меньше ядер — хуже параллелизация внутри модели). Прежде чем выбирать
минимальную конфигурацию для прода, стоит перепроверить RTF на ней же.

Альтернатива постоянному инстансу — **поднимать по требованию**: Cloud
Function дергает `yc compute instance create` при постановке встречи в
очередь, обрабатывает, останавливает инстанс (не удаляет — быстрее
следующий раз). Это резко снижает стоимость при нечастой нагрузке, но
добавляет задержку (холодный старт инстанса + загрузка модели — видели в
замерах 30–45 секунд) и требует отдельного кода управления жизненным
циклом, которого сейчас нет. Не реализовано — только вариант на будущее,
если объём встреч окажется низким.

### SpeechKit STT

Не меняется — API вызывается так же, как сейчас. Отдельно оценивался
только в рамках тестов на бенчмарк-корпусах:
≈ 0.20 ₽/минуту аудио (async-режим).

## Разница вариантов, которые обсуждались

### Один диаризатор на всё или два в паре

| | Один streaming-sortformer | Два (Sortformer + pyannote) |
|---|---|---|
| Стоимость инстанса | Одна модель в памяти | Обе модели в памяти одновременно, RAM почти вдвое |
| Качество ≤4 спикеров | Лучшее (DER 6.1%) | Такое же |
| Качество >4 спикеров | Плохое — слоты фиксированы, лишние сливаются | Хорошее — pyannote видит их |
| Сложность кода | Простая — один HTTP-вызов | Нужна логика переключения (см. ниже) |

Рекомендация из замеров: **два бэкенда**, с переключением по числу занятых
слотов Sortformer — это не требует предзнания состава встречи (которое,
как показала проверка, чаще неверно, чем верно) и даёт лучший результат
в обоих режимах. Логика переключения описана в
[services/diarization/README.md § Сколько спикеров занимает Sortformer](../services/diarization/README.md),
но **код переключения ещё не написан** — сейчас есть только сами сервисы
и фабрика `makeDiarizer`, которая умеет поднять любой из них по одной
переменной окружения. Автоматического выбора между ними нет.

### GPU или CPU

Не обсуждается всерьёз — GPU-квота в аккаунте `rnd-lab` равна нулю
(проверено `yc quota-manager quota-limit get`), и это не вопрос денег, а
отдельная заявка в поддержку Yandex Cloud. К тому же все три бэкенда
показали приемлемый RTF на CPU (0.04–0.52×), так что GPU не требуется по
существу — только по прихоти инфраструктуры.

### diart и EEND-EDA

Сознательно не внедряются — см.
[services/diarization/README.md](../services/diarization/README.md) для
причин (лицензия `segmentation-3.0`, отсутствие чекпоинта CALLHOME).

## Шаги внедрения, когда доступ будет выдан

1. **Выдать права.** Заказчик (владелец `cloud-stroytehekspert`) выполняет:
   ```bash
   yc resource-manager folder add-access-binding b1gcdsls1ovvfo2gf5j3 \
     --role functions.editor \
     --subject serviceAccount:ajed8u4l8ikhknm0s3jd
   yc resource-manager folder add-access-binding b1gcdsls1ovvfo2gf5j3 \
     --role api-gateway.editor \
     --subject serviceAccount:ajed8u4l8ikhknm0s3jd
   ```
   Либо выдаёт доступ другому сервисному аккаунту / собственному профилю —
   кому удобнее катить деплой.

2. **Выбрать конфигурацию инстанса** — см. таблицу стоимости выше.

3. **Поднять постоянный инстанс** с сервисом диаризации:
   ```bash
   services/diarization/deploy/create-instance.sh streaming-sortformer \
     --registry <registry-id> --sa <id> --subnet <id>
   ```
   (сначала dry-run без `--confirm` — печатает план и ничего не создаёт).

4. **Слить эту ветку** в `main` (уже проверенный PR-diff, единственное
   отличие — доступ, не код).

5. **Задеплоить** с новыми переменными в `scripts/.env.deploy`:
   ```bash
   ASR_PROVIDER=smart
   DIARIZER=streaming-sortformer
   DIARIZER_URL=http://<ip постоянного инстанса>:8000
   GROQ_API_KEY=...   # нужен для транскрипции, если ещё не задан
   ```
   Таймаут воркера автоматически поднимется с 60s до 600s — уже учтено
   в `scripts/deploy.sh`.

6. **Тестовая встреча.** Загрузить одну реальную запись через прод-интерфейс,
   сверить протокол на глаз — это шаг, который планировался сегодня и
   упёрся в доступ.

7. **Мониторинг первую неделю** — сравнивать долю встреч, где число
   найденных спикеров совпадает с ожидаемым (это легко логировать: у
   диаризатора есть `num_speakers_detected` в ответе).

## Что не сделано и почему

- **Постоянный инстанс не поднят** — блокирован отсутствием доступа, не
  технической причиной.
- **Автопереключение Sortformer↔pyannote** — есть измеренные данные и
  понятное правило, но код переключения не написан. Оценка: небольшая
  задача, HTTP-вызов к Sortformer, проверка занятых слотов, при полной
  занятости — второй вызов к pyannote. Не начиналась.
- **Автомасштабирование "по требованию"** — описано как альтернатива
  постоянному инстансу, не реализовано.
- **diart, EEND-EDA** — по решению из предыдущей сессии, не в приоритете.
- **Whisper vs SpeechKit по WER** — не измерено, нужен `GROQ_API_KEY`,
  который заказчик планировал предоставить позже.

## Как проверить эту ветку локально, не трогая прод

Всё из `services/diarization/` можно поднять на любом временном
CPU-инстансе (как делалось во всех замерах) без каких-либо прав в проде —
только Object Storage и SpeechKit API, которые уже доступны:

```bash
cd services/diarization
docker compose up streaming-sortformer   # или через Dockerfile.cpu без GPU
curl -F audio=@meeting.wav http://localhost:8003/diarize
```

Полная инструкция — [services/diarization/README.md § Быстрый старт](../services/diarization/README.md).
