# Эксперимент: выбор модели YandexGPT для LLM-коррекции расшифровки

**Дата:** 2026-06-10
**Вопрос:** какая модель — `yandexgpt-lite` или `yandexgpt` (Pro) — лучше подходит
для задачи коррекции ASR-транскрипта, и окупается ли разница в цене.

## Методика

- Корпус: 4 кейса × 6–10 реплик, строительная тематика (домен заказчика).
  Каждая реплика — пара «эталон / реалистичный выход ASR» (паттерны ошибок
  списаны с реального поведения SpeechKit: разрыв слов, числа словами,
  искажение терминов, бессмыслица на шуме).
- Профили кейсов: плотная терминология / числа-даты-деньги / чистый текст
  (проверка на гиперкоррекцию) / шумная запись.
- Протокол обмена — line-ID (прототип будущего refine-пайплайна):
  вход `[N] Спикер X: текст`, выход `[N] исправленный текст`. Без JSON.
- Метрика: WER (scripts/benchmark/lib/wer.mjs), 2 прогона на кейс, temperature 0.25.
- Раунд 1 выявил артефакты корпуса/метрики и слабость промпта → раунд 2
  с исправленным корпусом и ужесточённым промптом (политика числительных,
  запрет удалять слова). Итоговые числа — по раунду 2.

## Результаты (раунд 2)

| Метрика | yandexgpt-lite | yandexgpt (Pro) |
|---|---|---|
| WER до коррекции | 18.4% | 18.4% |
| **WER после** | **6.8%** | **5.3%** |
| Восстановление качества | 63% | 71% |
| case-1 термины | 24.5% → 4.9% | 24.5% → **3.9%** |
| case-2 числа/деньги | 36.7% → 11.4% | 36.7% → **6.3%** |
| case-3 чистый (гиперкоррекция) | 0.0% → **0.0%** | 0.0% → **0.0%** |
| case-4 шумный | 12.3% → 11.0% | 12.3% → 11.0% |
| Format compliance (line-ID) | 100% | 100% |
| Латентность (сред.) | 2.2 с | 2.2 с |
| Цена, ₽/1000 токенов (sync)* | 0.20 | 1.20 |
| **Стоимость коррекции 60-мин встречи** | **~10 ₽** | **~59 ₽** |

\* Цены требуют проверки на aistudio.yandex.ru (страница за CAPTCHA на момент
эксперимента); соотношение 6× стабильно. Async-режим (`completionAsync`)
исторически ~2× дешевле — наш refine асинхронный по природе, стоит использовать.

## Качественные находки

1. **Lite подменил дату**: «до двадцатого июня» → «до двадцать первого июня».
   Единичный случай, но это худший класс ошибок для протокола с дедлайнами.
   Pro фактических подмен не делал ни разу.
2. **Pro в раунде 1 удалял контент** («Давайте по повестке» выброшено при
   парафразе). Вылечено правилом промпта «НЕ удаляй и НЕ сокращай сказанное»
   — в раунде 2 оба чистые. Правило обязательно для прод-промпта.
3. **Line-ID-формат надёжен на 100%** в 32 вызовах обеих моделей — против
   текущего JSON-формата, который молча падает в raw на длинных чанках.
4. Оба не восстановили «дюбельное смещение» из «зубное смещенное вырезание»
   без глоссария — в проде глоссарий проекта подаётся в промпт, ожидаемо
   закроет часть таких случаев.
5. Числовая политика в промпте (марки в технической форме, числительные
   словами) исполняется обеими моделями.

## Решение

| Место | Модель | Обоснование |
|---|---|---|
| **Кнопка «Улучшить расшифровку»** | **Pro (`yandexgpt/latest`)** | Явный запрос качества от пользователя; числа/деньги 2× точнее; ноль фактических подмен; ~59 ₽/час аудио приемлемо для user-triggered действия (и ~30 ₽ через async) |
| **Inline-коррекция в draft-фазе** | **Lite (`yandexgpt-lite/latest`)** | Гоняется на каждой загрузке; 63% восстановления достаточно для черновика; 6× дешевле; риск подмены чисел закрывается валидатором (ниже) |

**Обязательный страховочный механизм (для обеих моделей):** детерминированный
валидатор чисел/дат — после коррекции сравнить множество числовых сущностей
(цифры, числительные, даты) входной и выходной строки; при расхождении —
оставить исходную строку и пометить. Ловит и подмену даты Lite, и любое
числовое творчество Pro. Реализуется без LLM, копеечный.

## Ответ на вопрос «окупается ли inline-коррекция»

Сегодня inline-A2 работает на Pro и **бо́льшую часть времени молча отдаёт сырой
текст** (обрыв JSON → fallback) — т.е. мы платим за Pro и не получаем результат.
После починки на line-ID + перевода на Lite: ~10 ₽ за час аудио за реально
работающую коррекцию, которая кормит протокол (числа, решения, дедлайны).
Окупается. Pro оставляем за кнопкой.
